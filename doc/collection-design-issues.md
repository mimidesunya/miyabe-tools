# 収集の設計上の問題

2026-08-30 の作業で、会議録と例規集のスクレイパに多数の不具合が見つかった。
その多くは外部レビュー（codex / grok）に指摘されるまで気づけなかった。
個別の実装ミスというより、**同じ形の間違いが何度も出ている**。

この文書は、その形を並べて直す順序を決めるためのものである。
個々の不具合は [collection-gap-survey.md](collection-gap-survey.md) にある。

> **この分類は「排他的な原因分類」ではない。**
> 当初「14 件が 5 つの型に収束する」と書いたが、これは言い過ぎだった。
> 不具合に通し番号を振っていないので 14 という数自体が検証できないし、
> 粒度もそろっていない（型 C は 5 つの症状を 1 件にまとめ、型 A と E は
> 症状を個別に数えている）。分類が修正方法に引っ張られているものもある。
> 「次へ」が止まらないのは、総数を見ていないこと（型 A）より
> **進行の単調性と停止条件が無い**ことが直接の原因である。
> 番号を題名セルから読むのは parser の列対応ミスで、型 C は
> 「安全に直せない」という被害を増幅している要因にすぎない。
>
> 重なりを許す**設計チェックリスト**として使うこと。

---

## 型 A. 「取れた」と「全部取れた」を区別していない

**いちばん多い。** 取得した結果は記録するが、**取得元が何を持っていると
言っているか**を記録しない。だから「全部取れた」と「取れる分だけ取れた」が
同じ `complete` になる。

今日これに当たった不具合:

| 不具合 | 何を「全部」と誤認したか |
| --- | --- |
| legal-square が 100 件で打ち切られていた | 1 回の検索結果 |
| 「次へ」が最終ページでも押せて無限に回る | ページ送りの有無 |
| dbsr が本会議しか取らない | 入口メニューのリンク |
| 年度別一覧が全期間そろえば完了 | 期間に抜けが無いこと |
| 監査が「発見候補」を「収録」と誤読 | `meetings_index.json` |

いずれも「取得元に総数を聞いていない」ことが原因である。例規は詳細検索の
件数表示、会議録は検索フォームの会議種別が総数にあたる。今日
`source_coverage.offered_meeting_types` を足したのがその第一歩だが、
**会議録の一部にしか無く、例規には無い。**

**直し方**: 取得元が申告する母数（件数・種別・年度）を、収録結果と同じ粒度で
必ず保存する。収録がそれに届かないなら `complete` にしない。

ただし**母数の意味は系統で違う**。検索型と目録型を混ぜてはいけない。

| 系統 | 母数にあたるもの | 入れ方 |
| --- | --- | --- |
| legal-square | 件数表示の `/N件` と「N件を超え」 | 総数と上限に張り付いたかを保存する |
| d1-law（OpenSearch） | 検索結果の `total_count` | カテゴリごとに実ヒット数と比べる |
| taikei / g-reiki / joureikun / jourei-v5 / d1-law（静的） | **独立した件数表示は無い**。目録を歩いた結果が母数 | 「目録を最後まで歩けたか」を保存する |

目録型に「申告された総数」を求めると、無いものを探しに行くことになる。

**会議録側にも同じ区別が要る。** 会議種別を読み取れない dbsr の 19 自治体を
調べたところ、川越市には**検索フォームそのものが無く**、`Cabinet=5,6,7…` は
一覧リンクに含まれているだけだった。つまり「取得元が申告する種別」が存在しない。

これを「未確認」と記録するのは正しくない。読み取りに失敗したのではなく、
**申告するものが無い**からである。状態は少なくとも 3 つ要る。

| 状態 | 意味 | 判定に使えるか |
| --- | --- | --- |
| 申告あり | 取得元が種別や総数を出している | 使える。突き合わせる |
| 申告なし | 取得元にその概念が無い（目録型） | 使えない。別の根拠が要る |
| 未確認 | 読み取りに失敗した、まだ見ていない | 使えない。読み直す |

いまの実装は後ろ 2 つを区別していない。

### 母数は「総数ひとつ」では足りない（**一部対応済み**）

外部レビューで、母数を `declared_total` と `capped` のフラットな 2 つで持つ案を
否定された。**検索型は分割の葉ごとに持たないと意味を成さない。**
福島県は最上位の総数が 100（上限値そのもの）で、情報は「どの葉が上限に
張り付いたか」の側にある。

`work/reiki/<slug>/source_coverage.json` に次を書くようにした
（`scrape_state.json` は実行のたびに消えるので分けてある）。

```json
{
  "kind": "search",
  "declares": true,
  "cap_value": 100,
  "leaves": [{"kind": "条例", "span": "明治2.1〜令和8.12", "total": 418, "capped": false}],
  "capped_leaves": 0,
  "complete": true
}
```

`complete` は「上限に張り付いたまま割り切れなかった葉が 1 つも無いこと」。
件数が揃っていても、葉が 1 つでも上限なら完了ではない。

目録型は `walk_complete` と失敗ページ数で持つ（未実装）。
取得元が母数を申告しない場合は `declares: false` として、未確認と区別する。

`audit_reiki_consistency.py` はこれを読み、`切り替えてよい` の判定に使う。
記録がまだ無い自治体は `未確認` なので、いま切り替えてよい自治体は 0 である。

## 型 B. 「不明」と「不在」を同じ値で表している

- 会議種別の空リストが「委員会が無い」と「読み取れなかった」の両方を指していた
- マニフェストに行が無いのが「原典から消えた」と「取得に失敗した」の両方
- 索引対象 0 件が「本当に 0 件」と「列挙に失敗」の両方

**害**: 読み取り失敗が「問題なし」として通る。愛知県はこれで
「取得元も本会議のみ」と誤判定された。索引 0 件で旧文書が消えないのも同じ型。

**直し方**: 値の型に「未確認」を入れる。空配列・0・欠落を「無い」の意味に使わない。

## 型 C. 同一性を、表示用の値から作っている

**これは全系統の問題ではない。** 外部レビューで例規側を洗ってもらった結果、
**legal-square だけ**が該当で、他はすでに取得元の識別子を使っていた。

| 系統 | 同一性の作り方 | 型 C か |
| --- | --- | --- |
| legal-square | `sha1(題名, 番号, 公布日)` | **該当** |
| taikei / g-reiki | `/reiki_honbun/` のファイル名 | 該当しない |
| d1-law（静的・reiki.html ほか） | 法令ディレクトリ名 `hno` | 該当しない |
| d1-law（OpenSearch） | `houcd` | 該当しない |
| joureikun / legalcrud | `act/{id}.html` の `{id}` | 該当しない |
| jourei-v5 | `frame{id}` の `{id}` | 該当しない |
| 会議録 | `downloads/<年ラベル>/<会議種別>/` と `(年ラベル, 種別, 表題)` | **該当** |

legal-square は文書ごとの URL が無く、一覧の入口 URL しかマニフェストに入らない。
そのため表示値からハッシュを作るしかなかった、という経緯がある。
一覧行に内部キー（`onclick` の引数など）があるかは未調査で、そこが次の一手になる。

**害**: **抽出を直すと同一性が変わる。** 新しい名前でファイルが作られ、
古いファイルが残って索引に二重に載る。今日、愛知県で実際に起こし、
千代田区でも起こしかけた。番号抽出の不具合（44,201 行中 217 行）を
直せずにいるのもこれが理由。

**直し方**: 同一性は取得元の識別子（URL・文書 ID）から作る。表示用の値は
メタデータとして持つだけにして、変わっても保存先が動かないようにする。
**対象は legal-square と会議録だけ**で、他系統は現状のままでよい。

ただし**取得元の識別子も永続に安定とは限らない**。新潟市では取得元が ID 体系
そのものを変えていた（`H1419...` → `e402RG...`）。取得元 ID は、内部の不変な
識別子に対する**履歴付きの別名**として持つ方が安全である。

## 型 D. 「いま何を持っているか」の正本が複数ある

例規で言うと 3 つある。

| 場所 | 中身 | 更新のされ方 |
| --- | --- | --- |
| `html/` のファイル | 本文 | 取得のたびに増える。**減らない** |
| `source_manifest.json.gz` | 収録一覧 | 実行のたびに作り直す。**縮む** |
| OpenSearch | 検索対象 | `html/` を列挙して作る |

三者が食い違っても誰も気づかない。可視化する道具
（`tools/reiki/audit_reiki_consistency.py`）を作って測った結果:

```
対象 1749 自治体 / 食い違い 925 / 孤児の合計 16404 / 欠落の合計 52
```

**半数以上（53%）が食い違っている。** legal-square だけの話ではなく、
g-reiki・d1-law にも及ぶ。

| 自治体 | 系統 | ファイル | マニフェスト | 索引 |
| --- | --- | ---: | ---: | ---: |
| 川崎市 | d1-law | 1396 | **0** | 1396 |
| 新潟市 | g-reiki | 2744 | 1375 | 2744 |
| 倉敷市 | legal-square | 1000 | 100 | 1000 |

検索件数はファイル数と一致しているので、**利用者から見た欠落は無い**。
問題は「何を持っているか」が分からないことである。

孤児の中身も一様ではない。新潟市の孤児 1369 件はファイル名が
`H141902500010_j.html`、マニフェスト側は `e402RG00000001_j.html` で、
**取得元が ID 体系を変えた前後の 2 世代**が混在していた。旧世代にしか無い
文書（要綱・基準など）もあり、「もう公開されていない過去の文書」なのか
「新体系で取り漏らした」のか**判別できない**。

判別できないまま自動で消すのは危険なので、この道具は消さない。
まず見えるようにするのが型 D の第一歩である。

原典から消えた文書を片付ける経路が無いのも、保存先を変える修正ができないのも、
突き詰めるとこの型である。

**直し方**: 正本を 1 つに決める（マニフェスト）。索引はそこから作る。
ファイルはキャッシュとして扱い、正本に無いものは消してよい。
ただしそのためには**マニフェストが縮まない保証**が先に要る。

## 型 F. 取得元の集合をモデル化していない

会議録の URL 一覧は **1 自治体 1 URL** で、読み込み側も自治体コードを辞書の
キーにして後の行で上書きする（`gijiroku_targets.py`）。

米子市は本会議の検索システムを登録しているが、委員会会議録は市サイトの
別ページにある。**登録した取得元に総数を聞いても、この抜けは絶対に見つからない。**
型 A（1 つの取得元の中の網羅性）とは別の問題である。

**直し方**: 主キーを `(自治体, 取得元 ID)` にして、自治体の網羅性を
複数の取得元の合成として扱う。

## 型 G. 世代と公開の境界が無い

- マニフェストは収集の途中で最終パスへ逐次書かれる。gzip も一時ファイル経由
  ではない（`reiki_io.write_bytes`）。**中断したマニフェストと完成したものを
  区別できず**、書き込み中断でファイルが壊れうる
- OpenSearch の増分更新は現行 alias へ直接 bulk し、そのあとで旧世代を消す。
  途中で失敗すると新旧が混ざる
- `document_kinds.json` は索引の**列挙時**に書かれる。公開が失敗しても
  新しい時刻だけが残る

**直し方**: 世代付きの候補を作り、`完了 / 部分 / 失敗` を持たせ、検証してから
原子的に現行ポインタを切り替える。自治体単位の lock も要る。

## 型 I. 直すのに人が要る状態を、直す人がいないまま置いている

放置していれば治る不具合と、治らない不具合がある。治らない側は
**「人が確認したら直る」形で設計してある**が、確認する人がいない。

2026-09-06 の点検で見つかった形:

| 状態 | 件数 | なぜ止まるか |
| --- | ---: | --- |
| 取得元 URL が空 | 会議録 245 / 例規 27 | 巡回のキューに載らない。載らないので何も起きない |
| 一覧が縮んで確認待ち | 例規 10 | 正本を置き換えてよいかを人に聞く設計 |
| 文字情報のない PDF | 3,860 | OCR が無い。毎回同じように除外される |

**直し方**: 「人が見たら分かること」を、機械が繰り返し観測して確かめる形に
置き換える。

- 取得元 URL が空 → 探索を定期実行し、確信度の高い結果だけ実行時の上書きと
  して採る（`tools/tasks/discover_sources.py`）。登録簿は書き換えない
- 一覧が縮んだ → 同じ縮み方が日をまたいで 3 回再現したら取得元の変更として
  受け入れる（`tools/shrink_confirmation.py`）。一時的な失敗は毎回違う形で
  落ちるので、同じ識別子の集合が繰り返し出ることは考えにくい
- OCR は機能そのものが無いので、これだけは作るしかない

**見えていない状態は直せない。** 同じ日に、走査記録 5,218 本が 0600 で
置かれていて公開画面から読めていないことも分かった（型 J）。

## 型 J. 書けたことと、読めることを同じだと思っている

`tempfile.mkstemp` は 0600 でファイルを作る。それを `os.replace` で正規名へ
置くと、置いた先も 0600 になる。取得側（miyabe）は自分で書いたものを読めるので、
テストでも手元でも気づけない。**読むのは別の利用者**（公開画面の PHP は
www-data）だった。

会議録の 1,400 自治体が「取得範囲未判定」だったのは、走査記録を書いて
いなかったからではなく、書いた記録を公開画面が開けなかったからである。
例規側は別の書き方（`with_name('.tmp')` + umask）だったので同じ症状が出ず、
**片側だけ壊れていることに気づけなかった**。

**直し方**: 別の利用者が読む前提のファイルは、書き手の側で読める権限に
してから置く。`gijiroku_storage.WEB_READABLE_FILE_MODE`。配備の権限修復にも
戻す 1 行を入れ、取りこぼしが残らないようにする。

## 型 H. 取得元の住所が変わることを勘定に入れていない

登録簿 (`reiki_system_urls.tsv` / `assembly_minutes_system_urls.tsv`) は
取得元 URL を 1 行 1 本で持ち、**その URL が永続だと仮定している**。
実際には版番号や採番を URL に含む取得元があり、取得元の都合で消える。

2026-09-06 の点検で見つかった形:

| 取得元 | 変わり方 | 影響 |
| --- | --- | --- |
| 北海道町村会 (`h-chosonkai` / 同ホストの `taikei`) | `data/{自治体}/{版}/` の版が繰り上がり、旧ディレクトリごと 404 | 21 自治体、約 6,600 件が更新されない |
| 掛川市 (`d1-law`) | 静的目録から OpenSearch 型へ移行し、旧パスが接続ごと拒否 | 663 件が全滅 |
| 小清水町・三郷町（会議録） | 会議録の一覧が別ページへ移動 | 会議録が 1 件も見つからない |

**害は「壊れたことが見えない」ところにある。** 目録ページのローカル控えが
残っているので、走査は前回と同じ件数を数え、`collected == declared_total` に
なる。失敗するのは本文の取得だけなので、件数だけ見ていると気づけない。

**直し方**: 二段構えにする。

1. 版番号のように**変わると分かっている**取得元は、巡回の直前に生死を見て、
   消えていれば入口から引き直す（`tools/reiki/source_url_recovery.py`）。
   登録簿は git 管理なので実行中に書き換えず、上書きを
   `work/reiki/source_url_overrides.json` へ逃がす。上書きは「置き換える前の
   URL」を覚えていて、登録簿が直れば自動で外れる
2. 引き直す手順が無い取得元は、**本文が全滅した実行を完了にしない**。
   `missing_at_source` が目録の 2 割を超えたら、取得元の作り替えとして扱う

「取得元が消したから 404」と「こちらが取り損ねた」を分けることも、この型の
一部である。混ぜると、何度巡回しても消えない失敗が積み上がり、直せる失敗が
その中に埋もれる。d1-law では 80 自治体がこの形で、実体は取得元の目録に
載ったまま本文が公開されていない例規だった。

## 型 E. 状態の寿命が設計されていない

- `scrape_state.json` は実行のたびに消される。ここに永続情報を置いた私の
  修正は無意味だった（`batch.py` の `remove_stale_scrape_state`）
- 失敗した自治体は `previous_failed` になったら**誰も戻さない**。
  八丈町は 105 日間、巡回対象から外れていた
- `document_kinds.json` は索引の**列挙時**に書かれる。公開が失敗しても
  新しい時刻だけ残るので、表示が「検索可」になる
- 子プロセスに実行期限が無い。1 件固まると巡回全体が永久に止まる

**直し方**: 状態ごとに「いつまで有効か」「誰が消すか」「消えたらどう復帰するか」を
決める。永続情報と実行時情報を同じファイルに置かない。

## 直す順序

当初 型 D → C → A → B → E と書いたが、外部レビューを受けて二度組み替えた。
**「マニフェストを正本にする」を一度にやろうとしたのが誤り**だった。

1. **食い違いを見えるようにする（済）**
   `tools/reiki/audit_reiki_consistency.py`。壊す変更はここで止める
2. **台帳の意味を先に決める**
   型 C の不変な識別子、型 B の三値（あり / 無し / 未確認）、型 A の母数、
   型 E の寿命、型 G の世代を**同時に**定義する。順に足すと手戻りする
3. **既存の経路を変えずに、新しい台帳を並行して書く**
4. **旧ファイル名・旧索引 ID と新しい識別子の対応表を作る**
   1 対多、識別子不明、本文ハッシュ不一致は自動で統合しない
5. **マニフェスト由来の影索引を作り、現行と突き合わせる**
   件数ではなく識別子の集合と本文ハッシュで比べる
6. **条件を満たした自治体だけ alias を切り替える**
7. **観測期間を置いてから、旧ファイルを隔離する**（消すのは最後）

並行して進められるもの（順番を待たなくてよい）:

- 取得元 URL の失効を自動で拾う（型 H）— **対応済み**。北海道町村会の
  引き直しと、`missing_at_source` の分離を入れた

- マニフェストが縮まないようにする（型 D の一部）。系統ごとに落とし方が違い、
  `static_catalog` と `taikei` / `g-reiki` は失敗を `continue` で捨て、
  `d1-law` は行を必ず足すので縮みにくい
- 母数と「未確認」を消えないファイルへ保存する（型 A + B + E）
- 子プロセスの期限、失敗の再試行、自治体単位の lock（型 E）— 前 2 つは対応済み

### 切り替えてよい条件

件数が合っているだけでは足りない。少なくとも次を満たす自治体だけを切り替える。

- マニフェストが**完了した世代**として原子的に発行されている
- `--limit` や未確認、失敗ページ、検索上限の未解決が無い
- マニフェストの全行が本文ファイルとハッシュで対応する
- ファイルにしか無い文書が「履歴・旧 ID・重複・不明」に分類済み
- 消える文書が 1 件ずつ説明できる（明示的な墓標がある）
- 影索引と現行索引を、件数ではなく識別子の集合で比べてある
- 0 件・読み取り不能・実行中は**切り替えない**

**「マニフェストが縮まない保証」だけでは不十分**である。原典から本当に消える
文書もあるので、必要なのは「部分実行では現行世代を更新しない」
「削除は完了世代の明示的な墓標だけ」という保証になる。

## いま無理に直さない方がよいもの

- 例規の番号抽出（44,201 行中 217 行）。型 C そのものなので、1 の前にやると
  孤児ファイルを増やす。grok の提案（旧 stem のファイルがあれば使い続ける）なら
  先にやれるが、移行の複雑さが残る
- 会議種別の短縮名（「総務」「文教」など 161 自治体）。取得元の実データなので
  正規表現では解けない。型 A の母数と突き合わせる方が筋が良い
- ファイルにしか無い文書の自動削除。新潟市では旧 ID 世代にしか無い文書が
  見つかっており、過去資料なのか取り漏らしなのか判定できていない
