# 収集取りこぼしの調査と対応計画

調査日: 2026-08-30
きっかけ: 福岡県議会の議員連盟補助金を調べようとしたが、根拠となる委員会記録も
補助金交付規則も検索に出てこなかった。原因を追ったところ、福岡県固有ではなく
**全国規模の収集漏れ**であることが分かった。

このファイルは、担当を引き継ぐ人（AI を含む）が調査を再現し、続きを進めるための
記録である。**未完了の作業が残っている。** 「進め方」の章から読むとよい。

## 1. 何が起きているか（確定した事実）

### 1-1. 例規集: legal-square は検索件数に取得元ごとの上限がある（**原因判明・対応済み**）

`data/municipalities/reiki_system_urls.tsv` の `system_type=legal-square` は 103 自治体。
保存済み例規の件数（`/mnt/big/miyabe-tools/reiki/<slug>/html` のファイル数）を数えると、
**丸い数字に固まっている**。

| 保存件数 | 自治体数 |
| --- | ---: |
| ちょうど 100 件 | **55** |
| ちょうど 1000 件 | 7 |
| ちょうど 500 件 | 6 |
| ちょうど 250 件 | 3 |
| 101〜999 件 | 29 |
| 1000 件超 | 11 |

福島県（`07000-fukushima-ken`）が 100 件ちょうど。都道府県の例規が 100 件ということは
ありえないので、実データではなく打ち切りである。

他系統の中央値は 700〜800 件なのに対し、**legal-square の中央値は 100 件**。

`--per-target-limit` は `TAIKEI_LIKE_SYSTEMS = {"taikei", "g-reiki"}` にしか渡らないので
（`tools/reiki/scrape_all_reiki.py:134`）、**こちら側の件数上限ではない**。

#### 原因: ページ送りではなく、取得元ごとの検索件数上限

福島県の詳細検索を実際に開いて確かめたところ、**ページ送りは正常に動いていた**
（1 ページ 10 件・10 ページ）。問題は総件数のほうで、条件を空にした検索の結果表示が

> 1〜10件目/100件

と、**100 件で頭打ちになっていた**。種別を「条例」だけに絞っても、「規則」だけに絞っても
やはり 100 件ちょうど。一方「訓令」は 54 件、「委員会等規程」は 33 件と上限未満の値が出る。
つまり 100 は実データではなく、**この取得元に設定された 1 回の検索の上限**である。

保存件数が 100 / 250 / 500 / 1000 という丸い数字に固まっていたのは、
**取得元ごとに上限の設定値が違う**ためだった。福岡県は上限 1000、福島県は上限 100。

#### 落とし穴その 2: 「次へ」が最終ページでも止まらない

一覧の「次へ」は**最終ページでも無効にならず、押せてしまう**。押すと同じページが
返るだけなので、`a:has-text('次へ')` の有無と `disable` クラスだけを見ていると
**永久に回り続ける**。実際に福岡県の「規則」で 219 ページ目まで回っていた
（総数 317 件・7 ページで終わりのはず）。
件数表示「1～50件目/317件」の末尾番号が総数に達したら終わり、と直した。

このループが、担当交代前に「例規スクレイパが固まる」と見えていた現象の正体である
（出力が無いまま延々と回るので、外からは停止と区別が付かない）。

#### 落とし穴その 3: 不正な日付でも検索が「成功」して見える

上限を割るために制定年月日で範囲を絞ろうとしたところ、**明治1年1月1日**を始点にすると

> 年月日(FROM) に正しい日付をご記入ください。

と弾かれ、**検索が実行されないまま前の結果が残る**。件数表示も前のままなので、
黙って古い件数を読んでしまう。同じ理由で、検索直後に件数を読むと
前の検索結果を読み違えることがある（AJAX の差し替え待ちが要る）。

### 1-1-1. 他の例規システムに同じ上限は無い（確認済み）

legal-square と同種の打ち切りが他系統にもあるかを、保存件数で確かめた。

| 系統 | 対象 | 中央値 | 丸い数字 | 内訳 |
| --- | ---: | ---: | ---: | --- |
| taikei | 551 | 745 | 2 | 400×1, 750×1 |
| g-reiki | 516 | 827 | 3 | 1000×2, 750×1 |
| d1-law | 429 | 785 | 3 | 1000×2, 750×1 |
| **legal-square** | 103 | **101** | **62** | **100×49**, 1000×6, 500×5, 250×2 |
| h-chosonkai | 65 | 617 | 2 | 400×1, 600×1 |
| その他 | 59 | 707〜968 | 0〜1 | |

legal-square 以外は 400〜550 自治体で丸い数字が 2〜3 件しかなく、偶然の範囲。
中央値も 617〜968 で正常。**この形の取りこぼしは legal-square だけ**である。

なお `system_type=独自` の 26 自治体は対応スクレイパが無く、例規を 1 件も
取得していない（`SUPPORTED_SYSTEMS` に含まれない）。取りこぼしではなく未対応。

### 1-2. 例規集: 福岡県で交付規則が欠けていたのも同じ原因（**対応済み**）

`legal_square.py` の冒頭には元から「詳細検索は最大 1000 件で打ち切られる」と
書かれていた。福岡県はこの上限が 1000 で、条件を空にした 1 回の検索では
1000 件で切られるため「福岡県補助金等交付規則（昭和33年規則第5号）」が落ちていた。
1-1 と同じ話で、上限値が取得元ごとに違うだけである。

### 1-3. 会議録: 「委員会 0 件が 835 自治体（55%）」は**誤検出だった**

当初は `meetings_index.json` の会議名に「委員」を含むものが 1 件も無い自治体を数え、
1514 中 835（55%）が取りこぼしだと見ていた。**この数え方が間違っていた。**

会議種別の持ち方は取得元によって違う。voices 系は
「総務常任」「予算特別」「厚生経済」のように**「委員会」の語を落とした形**で持つ。
港区（6455 会議）を「委員会 0 件」と数えていたが、実際の `meeting_group` は
総務常任 1090・建設常任 1056・保健福祉常任 787 …と、委員会は**ちゃんと取れていた**。

数え直したのが `tools/gijiroku/audit_meeting_types.py`。
「委員会という語が無い」ではなく **「どの会議も本会議の言い回ししか持たない」**
を疑いの条件にする（会議数 200 件以上に限る。小規模議会は委員会を公開していない
ことが普通なので）。

| 系統 | 対象 | 本会議のみ | 種別不明 | 種別=表題 |
| --- | ---: | ---: | ---: | ---: |
| kaigiroku.net | 527 | 221 | 0 | 0 |
| kensakusystem | 139 | 65 | 1 | 0 |
| dbsr | 172 | 58 | 3 | 9 |
| gijiroku.com（voices 含む） | 83 | 13 | 0 | 19 |
| 独自 | 521 | 12 | 34 | 0 |
| static-kaigiroku-dir | 33 | 2 | 1 | 0 |
| site-gikai-pdf | 24 | 0 | 1 | 0 |
| **合計** | **1512** | **371** | **40** | **28** |

- **本会議のみ** — 委員会の入口を見落としている疑い
- **種別不明** — 会議種別が記録されておらず、この情報だけでは判定できない
- **種別=表題** — 会議種別が会議ごとに全部違う。種別として機能していない

### 1-3-1. 「本会議のみ」の大半は、取得元が本会議しか公開していない

疑わしいと出た自治体を取得元まで当たった結果、**多くはスクレイパの落ち度ではなかった**。

| 自治体 | 系統 | 確認したこと |
| --- | --- | --- |
| 鳴門市・沖縄市 | kaigiroku.net | API の会議区分ツリーに `/0/1/4/`（委員会）が**存在しない**。本会議だけ |
| 米子市 | kensakusystem | 入口に「ご覧になれるのは平成5年第378回臨時会以降の**本会議録**です」と明記 |
| 佐賀市 | gijiroku.com | 検索フォームの会議種別が「定例会」「臨時会」だけ。委員会の区分が無い |

比較のため委員会が取れている自治体も見た。渋谷区（kaigiroku.net）の会議区分ツリーには
`/0/1/4/8/10/`（全会議＞委員会＞常任委員会＞総務委員会）以下が並び、
スクレイパはこれを正しく拾っている。**`council_type_path` が `/0/1/` 始まりに限る絞り込みは
委員会を落としていない**（委員会も `/0/1/4/` 配下にある。`/0/2/` は「資料」なので除外が正しい）。

### 1-3-2. 区別が付くようにした（**対応済み**）

取得元は検索フォームや API で「こういう会議種別がある」と自分から示している。
それを `scrape_state.json` の `source_coverage.offered_meeting_types` へ残すようにした。
**提示された種別に委員会があるのに 1 件も収録できていない**なら取りこぼし確定、
**提示された種別にも委員会が無い**なら取得元が公開していないだけ、と機械で分かる。

| 系統 | 読み取り元 |
| --- | --- |
| dbsr | 検索フォームの会議種別（`select` とチェックボックスの両方。福岡市はチェックボックス） |
| kaigiroku.net | `councils/index` API の会議区分ツリー（`council_type_name2` 以下） |
| gijiroku.com / voices | 検索フォームの `KGTP` チェックボックスのラベル |
| kensakusystem | 読み取り不要。ツリーを全部歩いて取るので提示＝収録 |

全件取得をやり直さなくても済むよう、**種別の一覧だけを取りに行く**
`tools/gijiroku/probe_offered_meeting_types.py` を用意した。1 自治体あたり
数リクエストで終わる。

### 1-3-3-1. 補った一覧の会議種別が空だった（**対応済み**）

`missing_cabinet_list_pages()` が返す一覧の `meeting_group` を空のまま渡していたため、
そこから取れた会議が**種別なしで記録されていた**。愛知県は 1052 → 1368 会議に
増えたのに、増えた 316 件の種別が空で、委員会を取れているかを後から判定できなかった。
会議種別は補う時点で分かっているので、そのまま渡すよう直した。

**「件数が増えた」だけで確認を止めると、この種の穴は見逃す。**
必ず `audit_meeting_types.py` で種別まで見ること。

### 1-3-4. 年度別一覧が全期間そろっていても、本会議だけのことがある（**対応済み**）

`discover_list_pages()` は年度別一覧（`div.LibraryTable`）を読めた時点で
**そのまま完了として返していた**。ところが愛知県の一覧リンクは
`Cabinet=1`（本会議）ぶんだけで、それが 1996 年から 2026 年まで揃っている。
期間の抜けが無いので「全部取れた」ように見え、委員会が丸ごと欠けたまま
`source_coverage.state=complete` になっていた。

**対応済み**: 年度別一覧を読み終えたあとに検索フォームの会議種別と突き合わせ、
**一覧に出てこない種別ぶんを全期間の一覧として補う**
（`missing_cabinet_list_pages()`）。愛知県で実測:

```
修正前: [INFO] 会議一覧ページ 210 件
修正後: [INFO] 一覧に出てこない会議種別 91 件を全期間で補います
        [INFO] 会議一覧ページ 301 件
```

あわせて、会議種別の選択肢を探す範囲も広げた（`collect_cabinet_options()`）。
検索ページに無くても閲覧メニューまで見に行く。愛知県は検索ページに選択肢が
無かったため `offered_meeting_types` が空で記録され、**取りこぼしを
「取得元も本会議のみ」と誤判定していた**。

**当初の「835 自治体（55%）が取りこぼし」は誤りだったが、「6 自治体だけ」も誤りである。**
6 は現在の検査で確定できた**下限**にすぎない。理由は 1-3-6。

### 1-1-2. 例規の番号を題名から拾っている（**未対応・直すと二重登録になる**）

`legal_square.py` の `ROW_EVAL` は一覧行の `td` を**題名セルも含めて**返す。
`_cell_after_title` のコメントは「題名セルを除いた」と書いているが、除いていない。
そのため題名に「第○号」が含まれると、**番号を題名から拾ってしまう**。

実測すると legal-square のマニフェスト 44,201 行のうち **217 行（0.5%）**が該当した。

```
題名: 平成28年台風第10号豪雨災害の被災者に対する市税の減免に関する条例
番号: 平成28年台風第10号豪雨災害の被災者に対する市税の減免に関する条例   ← 題名がそのまま
```

**直すと二重登録になるので、いまは直さない。** ファイル名は
`stem_for(題名, 番号, 公布日)` なので、番号の取り方を変えると **stem が変わる**。
新しい名前でファイルが作られ、**古いファイルが残ったまま索引に載る**
（索引は `html/` を列挙する）。愛知県で踏んだのと同じ罠である。

**より安全な直し方**（grok の提案）。掃除を先にやらなくても済む。

1. 番号の取り方は直す（題名セルを番号の候補から外す）
2. ファイル名は**旧計算法と新計算法の両方**を試し、`html/` に旧 stem の
   ファイルがあればそれを使い続ける。無いときだけ新 stem で作る
3. マニフェストの番号欄は正しい値に更新してよい（ファイル名は旧のまま）

これなら既存の 217 件は孤児にならず、新規だけ正しい番号になる。
ファイル名まで揃えるのは、掃除の仕組みができてから一度だけやれば足りる。

（当初は「縮まない保証を付ける」→「掃除を入れる」→「番号の取り方を直す」の
順序を考えていたが、それはファイル名まで一斉に直す場合の順序だった。）

影響は 0.5% で、内容は「番号欄に題名が入っている」こと。題名が同じ例規が
2 件あって両方とも題名由来の番号になった場合は stem が衝突して片方が落ちるが、
現在のマニフェストでは観測されていない。

### 1-3-7. 会議種別として使えない値が入っている（**一部対応済み**）

監査は `meeting_group` を委員会か本会議かで振り分けるが、**どちらとも判定できない値**を
持つ自治体が 161 ある。中身は 3 種類だった。

| 形 | 例 | 扱い |
| --- | --- | --- |
| 委員会名を短く持つ | 北海道「総務」「総合政策」「環境生活」、広島市「総務」「水道」「文教」 | 実データ。判定できないだけ |
| 一覧の見出しをそのまま入れた | 千代田区「トップページ」（6100 会議中 **2421 件**） | **不具合**。対応済み |
| 会議ではないものを種別にした | 尼崎市「令和８年３月 議会報」 | 取得元の構成どおり。表題側に委員会名がある |

千代田区の 2421 件は会議としては実在する（日付・本文・`Cabinet=2` 付きの一覧 URL）。
一覧ページの見出しを会議種別にしていたため、案内文言が入っていた。
**対応済み**: 見出しが案内文言のときは、一覧 URL の `Cabinet` と検索フォームの
選択肢を突き合わせて名づけ直す（`relabel_navigation_groups()`）。
突き合わない場合は空にする。使えない値を残すより、無いと分かる方がよい。

短く持つ形（161 のうち大半）は実データなので直しようがない。
**監査の委員会件数はこれらの自治体では過少に出る**ことを承知して使うこと。

### 1-3-6. この検査で分かるのは「登録した URL の中身」だけ（**重要な限界**）

外部レビュー（codex）に結論を否定させたところ、**私が根拠に使った例が反証された。**

米子市を「取得元が本会議しか公開していない」証拠として挙げていた。入口に
「ご覧になれるのは平成5年第378回臨時会以降の本会議録です」と明記されていたためである。
しかし米子市議会のサイトには **`/24735.htm`「委員会会議録」という別ページ**があり、
予算決算委員会・原子力発電問題等調査特別委員会・基地問題等調査特別委員会などの
記録が公開されていた。登録している検索システムに無いだけだった。

`assembly_minutes_system_urls.tsv` は **1 自治体 1 URL** なので、この形は構造的に見えない。

見えないものが他にもある。

| 見えないもの | 内容 |
| --- | --- |
| 別 URL での公開 | 上記。米子市のほか小美玉市・赤磐市も同じ形（codex 指摘、未検証） |
| 本文の取得結果 | `meetings_index.json` は**発見した候補**の一覧。候補にあっても本文が取れていないことがある |
| 一部だけの欠落 | 委員会が 1 件でもあれば判定から外れる。特定の委員会や年度だけ欠けているのは見つからない |
| 会議種別の読み取り漏れ | 福岡市がチェックボックスだった件は対応済み。他の形が残っている可能性はある |
| 未確認の 79 自治体 | kensakusystem 65・独自 12・static 2 は突き合わせる手段が無い |

**したがって「取りこぼしは 6 自治体」は言えない。言えるのは「6 自治体は確実に
取りこぼしている」まで。** 判定の名前も「取得元も本会議のみ」から
**「登録先は本会議のみ」**へ改めた。

#### これを埋めるには

1. 「登録先は本会議のみ」と出た 233 自治体について、議会サイトを見て
   **委員会記録の別 URL が無いか**を調べる。既存の URL 調査手順
   （`doc/assembly-minutes-url-survey.md`）と同じ作業になる
2. `assembly_minutes_system_urls.tsv` を 1 自治体複数 URL に対応させる
3. 会議種別の読み取りを `select` 以外（チェックボックス等）へ広げる

### 作業のときに踏んだ罠（同じ失敗を繰り返さないために）

**1. 保存先が変わる修正は、旧成果物の掃除まで含めて 1 組で考える**

会議録の保存先は `downloads/<年ラベル>/`、例規のファイル名は
`stem_for(題名, 番号, 公布日)`。どちらも**取得した値がそのまま保存先になる**ので、
値の取り方を直すと保存先が変わり、旧ファイルが残って索引が二重になる。
索引はディレクトリを列挙するので、マニフェストから消えても索引からは消えない。

愛知県で実際に起こした。番号の取り方の修正（1-1-2）を保留しているのも同じ理由。

**2. 長い取得を先に流して、あとからコードを直さない**

愛知県の取り直しを 16:15 に開始し、年ラベルの修正を 16:27 にデプロイした。
Python はプロセス起動時にモジュールを読むので、**1 時間以上かけた取り直しは
修正前のコードで走り切った**（2993 件中 1936 件が「全期間」のまま）。
直してから流し直すしかない。

**3. 掃除には必ず「減っていないこと」の確認を付ける**

上の取り直しのあと `全期間/` を消す手順を用意していたが、
「年別のファイル数 ≧ 全期間のファイル数」を条件にしていたため
`[ABORT] 年別が少ないので消さない` で止まり、データを失わずに済んだ。
条件を付けていなければ 2247 ファイルを消していた。

### 放置したときに何が治り、何が治らないか

**取得まわりは放置で治る。** celery beat が生きていて（`miyabe-tools-scraping-scraper-beat-1`）、
会議録・例規とも 1 日おきに周期取得を投入する。各自治体は
**前回の確認から 30 日経つと再取得の対象に戻る**（`tools/freshness_metadata.py`
の `FRESHNESS_SKIP_DAYS = 30`）。周期取得は `--index-dispatch celery` なので
OpenSearch の増分更新も自動で走る。

`data/background_tasks/*_snapshot.json` の `last_checked_at` から、対象に戻る時期は次のとおり。

| 対象 | 前回確認 | 再取得の対象に戻る |
| --- | --- | --- |
| legal-square 103 自治体 | 2026-08-02〜08-03 | **2026-09-01 頃** |
| dbsr の取りこぼし 4 自治体 | 2026-08-06〜08-08 | **2026-09-05 頃** |

修正済みのスクレイパはサーバー上のファイルと一致していることを確認済み
（`tools/reiki/scrapers/legal_square.py` ほか 5 ファイル）。
6 章のジョブを全部止めても、上の日付以降に順次直っていく。

### 子プロセスが固まると巡回全体が止まっていた（**対応済み**）

`tools/tasks/batch.py` は子プロセス（自治体 1 件のスクレイパ）に実行期限を持たず、
停止シグナル以外では打ち切らない。しかも heartbeat は子の進捗と無関係に更新される
（`refresh_active_worker_heartbeats()`）。そのため **1 件が固まると task が
「実行中」のまま残り、celery は `task_is_running()` で次の周期取得を投入しなくなる**。
つまり 1 自治体のハングで巡回全体が永久に止まる。

legal-square のスクレイパは実際に固まる（一覧のページ送りが終わらない不具合。1-1）。
今回は手で殺したが、celery 経由で起きていたら全国の取得が止まっていた。

**対応済み**: 一定時間まったく出力しない子を打ち切る（`stalled_workers()`、
既定 `--target-stall-seconds 3600`）。正常でも長い自治体があるので、経過時間ではなく
**無出力の長さ**で判断する。打ち切られた自治体は `failed` として記録され、
次のサイクルで拾い直される（打ち切りは SIGTERM なので `previous_failed` には落ちない）。

### 外部レビューで見つかった穴（**対応済み**）

codex と grok に読ませて、自分では気づかなかった穴を洗い出した。確認できたものを直した。

| 指摘 | 内容 | 対応 |
| --- | --- | --- |
| 子プロセスの実行期限 | 1 件固まると巡回全体が永久に止まる | `stalled_workers()` を追加 |
| 年ラベルの衝突 | 補完一覧の会議が年をまたいで 1 件に潰れる | 開催日から年を組み直す |
| 検索の差し替え待ち | 待ちきれないと古い件数のまま「分割不要」と判断 | `SEARCH_STALE` を導入し、1 度やり直してから分割 |
| ページ送りの固定待ち | 応答が遅いと残りページを捨てる | 件数表示が変わるまで待つ |
| 取得失敗の再試行 | 失敗した例規を「取得済み」に数えて拾い直せない | 成功時だけ記録する |
| 期間の右端 | 実行日より先の公布日がどの区間にも入らない | 年末までに広げる |

再レビューで (1)(2)(3)(4)(6) は塞がったことを確認済み。

年ラベルの衝突は影響が大きく、**愛知県は 1052 → 1368 → 2993 会議**と増えた
（1368 は年ラベル修正前で、同じ月日が年をまたいで潰れていた分）。

#### 年ラベル修正で持ち込んだ回帰（**対応済み**）

保存先は `downloads/<年ラベル>/` なので、年ラベルを直すと**保存先も変わる**。
修正前に取った `全期間/` が残ったまま年別ディレクトリへ入り直すため、
索引は `downloads` 配下を全部列挙する（`scraped_source_records.py`）ぶん
**同じ会議を二重に登録する**。愛知県 1 自治体・587 ファイルが該当した。

取り直しの完了を待ち、年別ぶんが `全期間/` ぶんを上回っていることを確かめてから
削除して再索引する手順を流した（`/tmp/aichi_cleanup.sh`）。

**原典から消えた文書を索引から取り除く経路が無い**ため、この種の保存先変更は
そのまま二重登録になる。保存先を変える修正のときは必ず旧成果物の掃除まで含めること。

残るのは次の 2 つ。

- **単月でも件数上限に張り付く場合**は、警告して超過分を捨てる。種別と月より細かい
  分割軸（番号・所管）は入れていない
- **来年以降の公布日**は区間に入らない

### 一度失敗した自治体は永久に巡回対象から外れていた（**対応済み**）

上の「30 日で対象に戻る」を実測で確かめたところ、**戻らない自治体があった**。

| | 30 日以上放置 | うち status=failed |
| --- | ---: | ---: |
| 例規 | 6 | **6** |
| 会議録 | 45 | **45** |

`tools/tasks/priority.py` は実エラーで失敗した自治体を `previous_failed`
（score=0）として巡回から外す。手動の `--retry-failed` を待つ設計だが、
celery の周期取得はこのフラグを渡さないので**誰も再試行しない**。
八丈町の例規は 2026-05-17 から 105 日間、対象に戻っていなかった。

**対応済み**: 失敗から `FAILED_RETRY_DAYS = 7` 日経ったら自動で 1 度やり直す
（`failure_is_retryable()`）。すぐに再実行しない元の意図は保ちつつ、
放置で永久に止まる状態をなくした。

なお失敗しても直近 30 日以内に成功記録がある自治体は、そちらの判定が先に効くので
再取得は最大 30 日先になる。永久に止まることは無いが「必ず 7 日後」ではない。

適用後の選定:

```
例規:   failed_retry=39  → 実行対象 35 自治体
会議録: failed_retry=60  incomplete=36
```

**放置では治らないもの（残り）:**

1. 取得元の作りが変わって失敗し続ける自治体は、再試行を繰り返すだけで直らない。
   `--list-targets` の `failed_retry` をときどき見て、繰り返し失敗しているものは
   個別に直す
2. 会議種別にあたる仕組み（`offered_meeting_types`）は kensakusystem と独自系には
   無い。この 2 系統の取りこぼしは機械では判定できない
2-2. **議会が別の URL で委員会記録を公開している場合は、いまの仕組みでは
   永久に気づけない**（1-3-6）。URL 一覧が 1 自治体 1 URL のため
3. **索引の rebuild を途中で止めると、alias が 2 つの index を指したまま残り、
   以後の通常の索引更新がすべて拒否される**（`build_opensearch_index.py`）。
   rebuild タスクに自動の再開・復旧は無い。現状は両 alias とも index 1 つで健全。
   rebuild を流すときは最後まで完走させること
4. 原典から消えた文書を索引から取り除く経路が無い。ローカルに残ったファイルは
   毎回そのまま索引される
5. 取得済みの会議録は同じ URL では取り直さない（`gijiroku_planning`）。
   原典が同じ URL のまま訂正された場合、古い本文が残る

## 走査記録を「消えない場所」へ移した（2026-08-30）

### 何が起きていたか

会議録側は、取得元をどこまで歩けたかを `scrape_state.json` の
`source_coverage` に書いていた。このファイルは `tools/tasks/batch.py` の
`remove_stale_scrape_state()` が**実行の頭で消す**。結果:

| 影響 | 中身 |
| --- | --- |
| 判定が死んでいた | dbsr の「前回 complete なら partial_planned に落とさない」は、消された直後のファイルを読むので常に偽。毎回いったん落ちる |
| 記録が消える | 実行が途中で殺されると、全部歩けたという記録ごと消える |
| 実行中が「記録なし」 | 監査は走っている最中の自治体を全部「走査状態不明」と数える |
| 公開画面が空振り | `homepage_gijiroku_source_coverage()` も同じ場所を見ていた |
| 再投入されない | `priority.py` はファイルが無いと即 `(0,0)` を返し、走査記録を見ずに終わる |

これは例規側の `offered_meeting_types` で一度踏んだ形と同じである。
そのときは 1 つの項目だけ直し、**同じファイルにある他の項目を見直さなかった**。

### 直したこと

- 会議録も `source_coverage.json` に分けた。写しは `save_state()` の中で取る
  （呼ぶ側に覚えさせると必ずどこかで忘れる）
- 写しと state の両方があるときは `updated_at` が新しい方を返す
- 写しの書き込み失敗を黙って捨てず、警告を出す
- 読み手（監査・優先度・公開画面）を全部写しへ寄せた

### 移行で誤ったこと

サーバ上の既存 `source_coverage` を 782 自治体分コピーし、
「782 自治体の走査記録を救出」と報告した。**これは誤りだった。**

内訳を数え直すと `状態なし 610 / complete 164 / partial_planned 4 /
partial_recent_only 4`。610 件の中身は
`{"offered_meeting_types": [...], "offered_types_probed_at": "..."}` で、
**probe が残した会議種別であって走査記録ではない**。
実際の走査記録は dbsr の 172 件だけだった。610 件は撤収した
（会議種別が `offered_meeting_types.json` に残っていることを確かめてから消した）。

grok が「782 は probe 対象（kaigiroku.net 527 + dbsr 172 + gijiroku.com 83）と
同じ数だ」と指摘し、数えて確かめて分かった。**件数が一致することを
根拠と取り違えていた。**

## 「発見した」しか記録していなかった 610 自治体

kaigiroku.net と gijiroku.com は `mode` と `updated_at` しか書かず、
`state` を一度も書いていなかった。監査からは永久に「走査状態不明」になる。
発見した件数だけでは、全部歩けたかどうかは分からない（型 A）。

- kaigiroku.net: 取得元が示した年の数と、実際に歩いた年の数を控える
- gijiroku.com: 開けなかった年度ページ、`BOTTOM` フレームが無くて飛ばした
  年度ページを数える。どちらも黙って `continue` していた
- 古い voices 型に落ちた場合は年度を歩く形ではないので `unknown` のまま

## 歩き切れなかったのに complete になる経路

codex が dbsr のページ送りに見つけた。「次へ」の click 失敗、次ページの
goto 失敗を `break` するだけで `failed_list_page_count` に数えていない。
**後半のページを丸ごと落としても complete になる。**

数えるようにした。ただし「同じページが返って止まった」場合は、最終ページでも
「次へ」を残す取得元があり得るので失敗には数えず、件数だけ記録する
（異常だという証拠がまだ無いため）。

例規側にも同じ形が残っていた。上限を検出できなかった全件取得
（`cap == 0`）で歩いた行数を捨てていたので、「次へ」が止まって 1 ページしか
取れなくても complete になる。分割走査と同じく突き合わせるようにした。

## 記録の版

母数の記録の意味は 2 度変わったのに `version` は 1 のままだった。
古い形式は上限に当たった葉をそのまま未完了としていたので、いまの
`complete` とは意味が違う。実際、茅ヶ崎市が `完了=False 未取得=0` という
読めない状態で残っていた（旧形式の残骸）。`version: 2` を切り、監査は 1 を
「旧形式」として信用しない。

## 歩き直しの途中で死んだ complete

「前回 complete なら落とさない」を効かせた結果、**歩き直しが途中で死ぬと
古い complete が残り、取得元が増えていても完了に見える**。
`walk_started_at` を控え、`updated_at` より新しければ確認前と分かるようにした。
優先度と公開画面も、この場合は complete を信用しない。

## 年ディレクトリが全角と半角に割れる（2026-08-30）

西尾市・甲府市・広島県・沼津市・取手市で、同じ年が `令和5年` と `令和５年` の
2 つのディレクトリに分かれていた。

### 最初の読み違い

古い方（全角、8/7 の更新）を、愛知県の `downloads/全期間` と同じ孤児だと考えた。
**これは誤り。** 中身を見ると:

| 側 | 中身 |
| --- | --- |
| 全角（古い） | 本会議（12月定例会、１月臨時会 …） |
| 半角（新しい） | 委員会（議会運営委員会、経済建設委員会、厚生委員会 …） |

**互いに補い合う別の中身**で、重複ではない。8/7 の実行は本会議しか取れておらず、
8/30 の実行が欠けていた委員会を取った。古い方を消していたら本会議を失っていた。

沼津市と取手市に至っては、古い側の方がファイルが多い（16 対 7、23 対 10）。
「新しい方が正しい」という一律の規則は、ここで確実に壊れる。

ファイル名だけで重なりを数えると、西尾市で 61 件が「同名あり」に見えた。
これも誤りで、`12月01日－本文.txt.gz` のような日付由来の名前が、
本会議と委員会の両方に現れるだけだった。**同名は同一ではない。**

### 直したこと

保存先を正規化した名前へ寄せるのが素直だが、それはできない。測ったところ
**全角の年だけを使っている自治体が 890 あり、99,549 ファイルが一度に孤児になる**。
愛知県で起きた事故の 170 倍になる。

代わりに、同じ年を指す保存先が既にあればそれを使う（`existing_year_dir`）。
新しく作るときだけ寄せて、既にある保存先は動かさない。

## 失敗を母数から落とす例規スクレイパ（2026-08-30）

codex の検証で、走査記録を書かない例規の系統が、失敗した分を
manifest から落として `n/n` で正常終了することが分かった。
10 件中 1 件落としても 9/9 に見え、キューは完了と読む。

| 系統 | 形 | 状態 |
| --- | --- | --- |
| `static_catalog`（joureikun / legalcrud / jourei-v5 など） | 個票の取得失敗を `continue` し、最後に `emit_progress(total, total)` で強制的に 100% | 直した |
| `taikei` / `g-reiki`（PHP） | 個票失敗を `continue` し、成功分だけの manifest で正常終了 | 直した |
| `d1-law` | 目録の欠けた枝を `continue`。失敗を数える変数が無い | 直した |

`static_catalog` は **目録に並んだ件数を申告とみなす**ことにした。
目録型に「総数」の表示は無いので、母数を別に探しに行くのは設計上やらない
（無い母数を探しに行く失敗に戻る）。目録そのものが申告である。

- `emit_progress(total - failed, total)` にして、失敗分を引く
- `source_coverage.json` に `kind: catalog` で記録する
- `--limit` で切った実行は完了にしない

### taikei / g-reiki（2026-08-30 追記）

`$failed` は数えていたのに、報告も母数への反映もしていなかった。
`static_catalog` と同じ形に揃えた。

- 25 件ごとの途中保存を `source_manifest.partial.json.gz` へ分けた
- `emit_progress(total - failed, total)` にして失敗分を引く
- `source_coverage.json` を書く。目録に並んだ件数が申告
- 前回より減ったら上書きしない（取り切れた走査でも 2 割超は拒む）
- 終了時に `Failed:` を出す

### d1-law（2026-08-30 追記）

目録の枝が開けないと `continue` して、その先の例規がまるごと見えなくなる
のに、数えていなかった。`get_hno_list()` が開けなかったページ数を返すように
して、`source_coverage.json` に残す。1 枝でも落ちていれば完了としない。

## 飛騨市: 母数の記録が初めて実在の取りこぼしを見つけた（2026-08-30）

母数の記録を入れて最初に `完了=False` が付いたのが飛騨市だった。

```
未取得: {'kind': '条例', 'span': '平成16.2〜平成16.2', 'reason': '単月でも上限100件'}
未取得: {'kind': '規則', 'span': '平成16.2〜平成16.2', 'reason': '単月でも上限100件'}
```

飛騨市は平成16年2月1日に4町2村が合併してできた。例規はその日にまとめて
制定されているので、制定年月日で割っても 1 日に集中して割り切れない。
**平成の大合併（2004〜2006）で生まれた自治体は同じ形になりやすい。**
これまで全自治体で静かに落ちていたはずで、母数を記録したから見えた。

### 打った手と、その結果

| 手 | 結果 |
| --- | --- |
| 日単位まで割る（検索フォームは日を受け付ける） | 実地で `平成16.2.1` まで降下。**1 日だけで 100 件超**と確定 |
| 種別ツリーの第2階層で割る（未使用の 32 件があった） | 仕組みは動くが、飛騨市の**条例・規則には子が無い**ので効かない |

残る軸として `enforceYmd4Detail`（施行年月日）がある。制定日が同じでも
施行日は分かれている可能性がある。**未着手。**

### 取り直しでマニフェストが縮んだ

日単位分割を入れた実行で、マニフェストが 1378 行から 786 行に上書きされ、
ディスクに残る 594 ファイルが孤児になった。突き合わせで確定した数字。

**利用者への影響は無かった。** 索引は markdown ディレクトリを列挙して作るので、
飛騨市は 1380 件が検索できたままだった。壊れたのは台帳だけである。
ただし台帳が縮むこと自体を止める必要があるので、
`write_manifest_guarded()` を入れた（前回より少ない行数では上書きしない）。

### 縮んだ原因: 一時的なものだった

同じ自治体を現行コードでもう一度走らせたところ **1378 行に戻った**。

```
収録 1378 完了 False 未取得 2 縮小 False 前回 786
```

日単位の分割による回帰ではなく、その 1 回だけ取得元（または接続）が
少なく返したものだった。**取得元は同じ条件でも違う件数を返すことがある。**

台帳はこれで自力で戻ったが、戻らなかった場合に備えて縮小ガードは要る。
ガードは「前回 786」を記録し、増えたので正しく上書きした。

なお **1 件取るたびに正本を上書きしていた**ため、ガードは最後の 1 回にしか
掛かっていなかった。走り始めた瞬間に 1 行まで縮み、途中で死ねばそのまま
残る。途中経過は `source_manifest.partial.json.gz` へ分けた
（legal-square・static_catalog・d1-law の 3 本とも同じ形だった）。

縮小ガードには逃げ道も要る。取得元が例規を廃止して本当に減ったとき、
正本が永久に古いまま固定されてしまう。**取り切れた走査なら区別が付く** ——
全部歩けたうえで少なかったのだから、取得元から消えたということ。
その場合だけ上書きを許す。

## 索引側の穴（取得とは別）

`--mode rebuild --slug X` や `--limit N` で作った部分的な索引を、
そのまま公開の alias に切り替えられた。切り替えると残りの自治体が
まるごと検索から消える。取得側をいくら直しても、再構築コマンド単体で
「欠けた索引を正常公開」が成立していた。

一部だけの再構築は alias 切り替えを拒むようにした。
作るだけなら `--no-switch-alias`、意図して公開するなら `--allow-partial-alias`。

## 別の自治体の例規が、その自治体のものとして公開されていた（2026-08-31）

「名前と中身が一致しているか」という観点で調べ直したところ、
**同名の自治体に、もう片方の URL が登録されていた**。

| 誤登録 | 実際に入っていたもの | 件数 |
| --- | --- | --- |
| 01696 北海道泊村 | 後志の泊村（01403）の例規 | 356 |
| 29452 奈良県川上村 | 長野県川上村（20304）の例規 | 621 |

保存ファイルで確かめた。両者の中身は完全に同じで、泊村は「古宇郡」が
31 件、川上村は「南佐久」14 件・「長野県」40 件。つまりどちらも
片方の自治体の例規である。

北海道に泊村は 1 つしかないので 01696 は重複。奈良県川上村は実在する
別の村なので、**その村の例規は 1 件も取れていないうえ、長野県の例規が
その村のものとして公開されていた**。

### 型 F の裏返し

設計メモの型 F は「1 自治体 = 1 URL」で、複数の取得元を持てないことだった。
これはその逆で、**1 URL = 複数自治体**である。同名の自治体があると、
片方の URL をもう片方にも登録してしまう。

### 直したこと

- 誤登録の 2 件を `unresolved` にして URL を外した
  （奈良県川上村の例規集は、村のサイトにリンクが無く未特定）
- 索引から 977 件（356 + 621）を削除、作業ディレクトリを `_archive` へ退避
- `tools/audit_shared_source_urls.py` を追加。同じ URL が複数の自治体に
  登録されていないか調べる。全国で他に該当は無い（会議録も 0 組）

### この観点は最後まで見ていなかった

29 回目まで「収録できたか」だけを見ており、両者とも「無い」で一致していた。
30 回目に観点を変えて初めて出た。**同じ問いを繰り返しても、
見ていない観点の欠陥は見つからない。**
