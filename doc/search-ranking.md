# 検索の並び順と近接優先

会議録・例規集の検索は OpenSearch alias を正とし、`/api/search` に一本化している。
Web 画面も MCP もこの API を通るので、並び順の仕様はここだけを見ればよい。

## 並び順の種類

| `sort` | 並び |
| --- | --- |
| `date` | 新しい順。ただし下記の条件を満たすと近接優先が働く |
| `relevance` | 関連度順（OpenSearch の `_score`） |

既定は Web 画面と MCP の会議録が `date`、MCP の例規集が `relevance`。

## 近接優先

AND 検索で語が離れていると、同じ文書に両方の語が出てくるだけで文脈は無関係、ということが
起きる。会議録は 1 文書が議会数日分の全文（数百 KB）なので特に起きやすい。そこで
**検索語が本文中で近くに現れた文書を、日付順より前に出す**。

近さ順に整列するのではなく、しきい値の内か外かで二値に分ける。同じ考え方は
LexisNexis や Westlaw の `/s`（同一文）・`/p`（同一段落）と同じで、法律文書検索では
標準的な扱い。

### 働く条件

すべて満たしたときだけ有効になる。ひとつでも外れると従来どおりの日付順。

- `sort=date`（`relevance` は元から近い語が上に来るので触らない）
- 検索語が 2 語以上
- 演算子を含まない素の AND 検索。`"..."`・`OR`・`NOT`・`NEAR`・括弧・`|`・先頭の `+`/`-`
  が入ると無効（`japanese_search_query_is_plain_and()`）
- 完全一致フレーズ指定がない（フレーズは位置を固定して探しているので重ねる意味がない）

### 実装

`miyabe_search_build_request()` がクエリをこう組み替える。

- AND 条件を `must` から `filter` へ移し、スコア計算から外す
- `should` に近接判定の `constant_score` を 2 本置く（語単位 `boost 2.0`、文字単位 `boost 1.0`）
- 結果として `_score` は 3 / 2 / 1 / 0 のいずれかにしかならない
- `sort` を `[_score desc, sort_date desc]` にする

`_score` の意味はこう。

| `_score` | 意味 |
| --- | --- |
| 3 | 語単位でも文字単位でも近い（最も確か） |
| 2 | 語単位で近い |
| 1 | 文字単位でだけ近い（複合語の救済） |
| 0 | 近くない |

これで「しきい値より近いものが先、その中では新しい順」「残りも新しい順」が検索 1 回で出る。
近さの度合いで整列するのではなく、しきい値の内か外かで前後に分けるのが狙い。内側では
語単位で当たったほうが確かなので先に置く。リランキングも追加インデックスも要らない。

応答には `proximity_ranked`（働いたか）と、各件の `proximity`（`_score >= 1` かどうか）が入る。
`_score` は関連度ではなくなるので、近接優先のときは `score` に載せない。

### しきい値

- 語単位: `body_terms` の `match_phrase` `slop = 25`（`MIYABE_SEARCH_PROXIMITY_SLOP`）
- 文字単位: `body` の `match_phrase` `slop = 40`（`MIYABE_SEARCH_PROXIMITY_CHAR_SLOP`）

`body_terms` は 1 形態素につき表層形と正規形の両方を入れている
（`japanese_search_tokenizer.py` の `document_terms_text()`）ので、slop はトークン数であって
語数ではない。25 トークンでおおむね 18〜21 形態素になる。`body` は CJK bigram なので
position がほぼ文字位置で、slop はそのまま文字数として読める。

25 / 40 にした根拠は 3 つ。

1. **実例**。本番データのランダムサンプルで距離帯ごとに中身を読むと、文字ギャップ 40〜80 が
   関連あり／なしの境目で、80 を超えると無関係な共起（「空き家」＋「野猿対策事業」、
   「情報公開」＋「使用料及び手数料徴収条例」）が混じり始める。語単位でも slop 15〜25 では
   劣化せず、40 で劣化した
2. **業界標準**。LexisNexis の `/s`（同一文）が約 25 語、`/p`（同一段落）が約 75 語。
   25 トークン ≒ 18〜21 形態素は `/s` とほぼ同じ粒度
3. **文の長さ**。本番データでは会議録の 1 文が中央値 35 文字・p75 61 文字、例規が
   中央値 22 文字・p75 41 文字

### なぜ 2 本見るのか

語単位のほうが精度は高い。`body`（bigram）だけだと「審議会」の中の「議会」を拾ってしまい、
本番データでも実際に誤ったヒットが出た。

ただし **索引側とクエリ側で Sudachi の分かち書きが食い違っている**。クエリ側は
「ふるさと納税」「情報公開」を 1 語に切るのに、索引の `body_terms` では
「ふるさと」＋「納税」、「情報」＋「公開」に割れていて、`match_phrase` が永久に当たらない
（会議録の索引は 2026-06-21 作成。それ以降に辞書の分割が変わったとみられる）。

これは近接優先だけの問題ではなく、既存の `multi_match(body_terms)` も複合語で空振りしている。
`simple_query_string` の `body` / `body.ngram` が拾うので表面化していなかっただけ。
根本的には索引を作り直して分かち書きを揃えるべきだが、会議録は 201GB あるので簡単ではない。

そこで文字単位を控えめな重みで足している。実測では `should` を 2 本にしても遅くならない
（Lucene は片方が当たれば他方の評価を飛ばす）。

### 速度

本番実測（`took`、ウォームアップ後）。

| クエリ | 変更前 | 語単位のみ | 文字単位のみ | 両方（採用） |
| --- | --- | --- | --- | --- |
| ふるさと納税 返礼品 | 40ms | 39ms（空振り） | 118ms | 48ms |
| 空き家 対策 | 47ms | 22ms | 114ms | 26ms |
| 議会 デジタル | 34ms | 113ms | 244ms | 58ms |
| 給食 無償化 | 40ms | 24ms | 59ms | 30ms |

例規集（145 万件・19.7GB）は 1 文書が短いのでほぼ増えない。AND 条件を `filter` へ移す分
スコア計算が消えるので、変更前より速くなる場合もある。

`slop` を小さくしても速くはならない。むしろ `slop=0` が最も遅かったので、しきい値は
速度と切り離して質だけで決めてよい。

近接はクエリごとに決まるのでインデックス時に持てない。`index_phrases` は `slop=0` 専用で
今回は効かない。

### 調べ直すとき

`work/proximity-sort/` に調査用のプローブを置いてある。いずれも読み取り専用。

- `probe4.py` — 2 語の距離分布、同一文に収まる割合、距離帯ごとの実スニペット、1 文の長さ
- `probe5.py` — slop 別のヒット率と速度
- `probe8.py` — `body_terms` と `body` にどのトークンが入っているかの突き合わせ
- `probe9.py` — 語単位 / 文字単位 / 両方の、ヒット率・速度・上位の質の比較

本番へは `deploy/remote_exec.py` で流す（`deploy.json` の鍵設定を使う）。
オプションは位置引数より前に置く（`command` が `argparse.REMAINDER` のため）。

```
python3 deploy/remote_exec.py --script-file work/proximity-sort/probe9.py --python deploy.json
```
